# ADR-0022: Reviewed cleanup of old system generations

- Status: proposed — the keep values below await the owner's confirmation
- Date: 2026-09-30

## Context

Every controller application and every client deployment adds a NixOS system
generation. Nothing removes them: the repository sets no `nix.gc`, no boot
entry limit and offers no guided way to free space. The Nix store therefore
grows until a controller or client runs out of disk, and the boot menu lists
every generation ever activated. Classroom clients have small disks and are
not continuously monitored.

Automatic collection would be the wrong answer here. Validation must never
collect garbage, a collection during deployment or PXE preparation could
remove paths another operation is about to use, and the controller store also
serves client closures through the signed cache. An administrator should see
what is kept and removed, choose when it runs, and get an honest result.

## Decision

Add one reviewed Maintenance operation, **Free disk space**, shared by CLI and
TUI, with the same plan/apply shape as client power control.

### What is removed and what is always kept

On each selected computer, only generations of the NixOS system profile
(`/nix/var/nix/profiles/system`) are removed. Always kept:

- the newest **K** system generations (proposed **K = 3**);
- the generation the computer is running (`/run/current-system`) and the one
  it booted (`/run/booted-system`), even if older than those K;
- every other garbage-collector root, in particular the controller's managed
  PXE roots under the Nixorium state directory and the prepared installer.

User profiles, home directories, the deployment repository, logs, operation
records and snapshots are never touched. After removing generations the
operation runs one ordinary Nix garbage collection (unreachable store paths
only) and rewrites the boot menu from the remaining generations.

A bounded boot menu is added to every managed host: the GRUB configuration
lists at most **B** generations (proposed **B = 10**, `boot.loader.grub.
configurationLimit`, overridable by the deployment with `lib.mkForce`). This
only limits menu entries; it removes no generation by itself.

### Review and confirmation

Plan resolves the controller and/or evaluated client identities, observes each
one read-only (generation list, which would be kept or removed, free space on
the store file system) and returns an expiring content-bound review token and
the one-word confirmation `CLEAN`. The review states that the exact amount of
space freed is known only afterwards, because a removed generation can share
store paths with the kept ones. Computers that are off or unreachable remain
visible and are never queued.

Apply validates token and expiry, takes the same operation lock as deployment
and PXE preparation (so it never runs during either), rechecks each target's
generation list and boot IDs, and refuses a target whose kept set changed
since review.

### Privileged execution

- Controller: a fixed systemd unit `nixorium-clean-generations.service` runs a
  store-backed script as root with no arguments; the keep count comes from its
  root-owned configuration generated by Nix. Sandbox as the existing apply
  units: `ProtectHome`, no network namespaces beyond local, `NoNewPrivileges`,
  write access only to `/nix` and `/boot`.
- Clients: the same fixed helper `nixorium-clean-generations` installed in every
  managed host generation, invoked over the existing non-interactive root SSH
  path with a fixed argument array (`--plan` or `--apply <expected-ids>`). No
  presentation value supplies a path, count, executable or shell fragment.

### Interrupted runs and results

Each computer reports `cleaned` (with free space before and after), `not-sent`,
`unchanged` (nothing to remove) or `unconfirmed`. Removing a generation and
collecting garbage are each safe to interrupt: the store stays consistent and a
later run finishes the work. An interrupted run is reported as unconfirmed with
the observed free space, never as success, and is not retried automatically.
The boot menu is rewritten only after generations were removed; if that step
fails the result says so, because the menu may still list removed entries until
the next successful application. Operation history records a bounded summary.

## Consequences

Administrators can reclaim space on demand with a review that names exactly
which generations go and which stay, while PXE preparation and deployments
keep their store paths. Rollback remains possible to the kept generations only;
the review says how far back that is. The controller may need to rebuild or
re-fetch client closures after a collection, which the next deployment does
normally. Scheduling, automatic collection and per-user profile cleanup remain
outside this decision.

## Open for confirmation

1. K = 3 kept system generations per computer (in addition to running and
   booted).
2. B = 10 boot menu entries.
3. The confirmation word `CLEAN`.
